# 收工沉淀

> 每次推进了某个项目，收工前无条件跑。

## 步骤

### 1. 更新 `进度.md`（只要动过项目就必须做）

找到对应条目，更新五项：**当前版本／状态／下一步／最近经手／更新日期**。

- 「下一步」写成可执行动作，不写「继续优化」
- 状态用统一标记：`进行中` / `等待用户确认` / `暂缓` / `已交付` / `已归档`
- 只改本次实际推进的条目，不重写整个文件
- 把刚动过的条目挪到最上面（按最近更新时间倒序）
- 项目结束移到「已归档」，不直接删

### 2. 判断是否有稳定新知识

重大任务的判定标准与沉淀边界见 `AGENTS.md` →「重大任务完成后的自动复盘」。

**只沉淀**：用户／领导确认的长期要求、稳定业务规则、反复适用的偏好、有效的策划与设计方法、
典型样本、常见风险及已验证的解决方式。

**不沉淀**：临时讨论、未确认猜测、一次性素材与路径、账号凭据、失败但无结论的尝试、
其他公司／求职／生活／医疗信息、工具专属配置。

**没有稳定新知识就不要为了留记录而改文件。**

### 3. 有新知识则更新 `卓望.md`

- 合并进对应章节，**优先修订原条目而非堆叠**
- 检查与现有规则是否冲突；有冲突保留最新已确认结论并说明替代关系
- 大段方案和交付成品存为独立文件，`卓望.md` 只留索引、规范、结论和可复用经验
- 同步修改文末「最后更新」日期

### 4. 判断是否要更新 `流程/`

发现了更优的执行顺序、新的踩坑点、新的验收项 → 更新对应流程文件。

注意分工：**业务知识进 `卓望.md`，执行步骤进 `流程/`。**
流程文件里不要复述知识内容，引用 `卓望.md` 章节名即可。

### 5. 提交推送

```
git add -A && git commit -m "docs: update zhuowang knowledge" && git push
```

推送后回读验证内容与本地一致。
推送失败必须明确说明当前使用版本和待同步内容，**不得声称两端已一致**。

### 6. 交付说明

向用户说清四件事：

1. 本次交付物是什么
2. 是否产生值得沉淀的长期知识
3. 更新了 `卓望.md` 就概述更新内容并给出提交
4. 没更新就说明原因

## 验收清单

- [ ] `进度.md` 对应条目已更新且挪到顶部
- [ ] 已判断是否存在稳定新知识，无则明确说明
- [ ] 有新知识时已合并进 `卓望.md` 对应章节并更新日期
- [ ] 知识与流程没有写串位置
- [ ] 已提交推送，且推送后回读验证
- [ ] 交付说明四件事齐全
